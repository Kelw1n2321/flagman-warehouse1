# Свежачок!

Учёт склада ресторана: продукты, партии, сроки годности, заказы, стоп-лист и горячие предложения.

Сайт: https://flagman-warehouse.onrender.com

## Что умеет

- показывает остатки по каждому продукту и по партиям, у каждой партии свой срок годности
- принимает поставки (каждая строка поставки становится отдельной партией)
- проверяет заказ: если хоть какого-то продукта не хватает, заказ отклоняется и остатки не трогаются
- сам собирает стоп-лист из блюд, которые нельзя приготовить
- подсказывает, какие блюда продвигать, чтобы продукты не испортились (горячие предложения)
- считает статистику и прогноз, когда что закончится и что надо заказать
- ведёт журнал всех движений по складу
- списанное попадает в корзину, откуда его можно вернуть на склад
- менеджер может закрепить блюдо в горячих предложениях (например, сезонное) или скрыть его
- раздел «Ходовые блюда» (только менеджер): рейтинг продаж за 7, 14 или 30 дней с динамикой
- у поставщика свой кабинет: он отправляет заявку, а менеджер принимает фактическое количество
- роли: менеджер видит всё, официант только заказы, меню, стоп-лист и горячие предложения
- есть светлая и тёмная тема и версия для телефона

## Как запустить

Нужны .NET 10 и Node.js 20 или новее.

Собрать интерфейс:

```bash
cd frontend && npm install && npm run build
```

Запустить сервер:

```bash
cd backend/Flagman.Api && dotnet run
```

Потом открыть http://localhost:5080. Локальные ID для входа лежат в `appsettings.Development.json`:
`1001` менеджер, `1002` официант, `1003` поставщик (его кабинет на http://localhost:5080/supplier).
При первом запуске создаётся база SQLite с демо-данными за неделю, сбросить их можно в настройках.

Если правишь интерфейс, удобнее `cd frontend && npm run dev`, тогда он открывается на http://localhost:5173
и сам обновляется при изменениях.

Через Docker с PostgreSQL:

```bash
ADMIN_IDS="1001:Максим" docker compose up --build
```

Сайт будет на http://localhost:8080. В этом режиме демо-данных нет.

## Вход и роли

Без входа сайт ничего не показывает. Каждый вводит свой ID.

ID задаются одним из двух способов:

1. Переменная окружения `Auth__AdminIds`, например `1001:Максим, 1002:Анна:waiter, 1003:ООО Фермер:supplier`.
   Формат `ID:Имя:роль`. Имя видно в меню, роль `manager` (по умолчанию), `waiter` или `supplier`.
   Если роль написана с ошибкой, запись не принимается, чтобы случайно не дать права менеджера.
2. `Auth:AdminIdHashes` в `appsettings.json`, тот же формат, только вместо ID его хеш (PBKDF2). Его можно держать
   в открытом репозитории. Строку для нового ID можно получить через `AdminDirectory.HashId("твой-id")`.

Что видит каждая роль:

| Роль | Доступ |
|---|---|
| менеджер | всё, включая ходовые блюда, корзину и заявки поставщиков |
| официант | заказы, меню (без редактирования), стоп-лист, горячие предложения |
| поставщик | только свой кабинет `/supplier`: каталог товаров и свои заявки |

Права проверяются на сервере: официант получит 403, даже если вручную откроет адрес склада.
Поставщик входит только в кабинете `/supplier`, сотрудники только на основном сайте.
У кабинета поставщика своя cookie, поэтому в одном браузере можно быть одновременно поставщиком и менеджером.

Вход живёт 12 часов. Чтобы ID нельзя было подобрать, больше 10 попыток в минуту делать нельзя.

## Кабинет поставщика

Отдельная страница `/supplier` на том же сервере. Поставщик выбирает товары из нашего каталога, указывает количество
и срок годности и отправляет заявку. Менеджер видит её в «Поставки → Заявки поставщиков» и принимает фактическое
количество (например, заявлено 20 кг, приехало 18) или отклоняет с причиной. После приёмки создаются партии на складе,
а поставщик видит у себя «Принята частично: 18 кг из 20».

## Ходовые блюда

Раздел только для менеджера (официант получает 403 и не видит его в меню). Блюда отсортированы по проданным порциям
за выбранный период: 7, 14 или 30 дней по времени ресторана. Считаются только выполненные заказы. Для каждого блюда:
сколько порций и заказов, доля от всех продаж, изменение к прошлому такому же периоду, график по дням и сколько порций
можно приготовить прямо сейчас (или что блюдо в стоп-листе). Можно отфильтровать по разделу меню. API: `GET /top-dishes?days=7&category=`.

## Корзина

Списание (порча, просрочка, автосписание) не пропадает, а попадает в раздел «Корзина». Оттуда можно:

- вернуть на склад: количество возвращается в ту же партию, в журнале появляется операция «Возврат из корзины»;
- удалить навсегда: запись пропадает из корзины, остатки не меняются, в журнале списание остаётся.

Вернуть просроченную партию нельзя, если включено автосписание, иначе она сразу снова уйдёт в корзину.
В статистике возвращённое списание не считается потерей.

## Правки горячих предложений

Менеджер может закрепить любое блюдо (например, сезонное) с пометкой и сроком «до». Закреплённые идут первыми
с меткой «Выбор менеджера». Можно и скрыть блюдо, даже если в нём скоро испортятся продукты. Скрытые видны
в разделе «Скрыто менеджером», откуда их можно вернуть. Официант видит итоговый список без кнопок.

## Деплой на Render

В репозитории есть `render.yaml`. В Render нужно выбрать New, потом Blueprint, выбрать этот репозиторий и нажать Apply.
После каждого пуша в main сайт пересобирается сам. Проверка, что сайт живой, идёт по адресу `/api/health`.

На бесплатном тарифе база лежит внутри контейнера, поэтому после перезапуска демо-данные создаются заново.

### Как считается склад

- Остаток продукта нигде отдельно не хранится, он считается как сумма его партий.
- Просроченная партия в остаток не входит и для блюд не используется. Её можно списать вручную или включить автосписание.
- Любая операция (приёмка, расход, списание, корректировка) записывается в журнал.
- Заказ: сначала считаем, сколько всего нужно каждого продукта, и сравниваем с остатком. Если чего-то не хватает,
  заказ сохраняется как отклонённый с причиной. Если всего хватает, продукты списываются по FEFO
  (сначала то, что раньше испортится) одной транзакцией.
- Блюдо попадает в стоп-лист, если какого-то продукта меньше, чем нужно на одну порцию.
  Раз в 30 секунд сервер проверяет сроки, потому что продукты портятся и без всяких действий.
- Сроки по умолчанию: больше 72 часов норма, от 24 до 72 скоро истекает, меньше 24 критично.
  Все даты считаются по часовому поясу ресторана (по умолчанию Москва).

### Горячие предложения

Для каждого продукта, у которого скоро истекает срок, ищутся блюда, где он используется. Каждому блюду ставятся баллы:

```
баллы = 100 × срочность × (0,35 + 0,65 × покрытие) × (0,5 + 0,5 × объём) × эксклюзивность
```

- срочность растёт от 0,4 до 1 по мере приближения срока
- покрытие показывает, какую часть продукта блюдо может израсходовать
- объём показывает, сколько порций нужно, чтобы израсходовать продукт
- эксклюзивность равна 1/√N, где N это сколько ещё блюд используют этот продукт

45 баллов и больше это высокий приоритет, от 20 средний.

### Прогноз

Берётся средний расход за последние 7 дней, и по часам моделируется следующая неделя. Так видно, когда продукт закончится,
когда блюдо уйдёт в стоп-лист и сколько надо заказать.

## API

Все запросы идут на `/api/v1`, без входа сервер отвечает 401 (кроме `/auth/*`), без нужной роли 403.

| Метод | Путь | Что делает |
|---|---|---|
| POST, GET, POST | `/auth/login`, `/auth/me`, `/auth/logout` | вход, кто вошёл, выход |
| GET | `/top-dishes?days&category` | ходовые блюда (менеджер) |
| GET | `/trash`; POST `/trash/{id}/restore`, `/trash/{id}/purge` | корзина (менеджер) |
| PUT, DELETE | `/hot-offers/overrides/{dishId}` | закрепить или скрыть блюдо, снять правку (менеджер) |
| GET, POST | `/supplier-requests`, `/supplier-requests/{id}/accept`, `/supplier-requests/{id}/reject` | заявки поставщиков (менеджер) |
| GET, POST | `/supplier/products`, `/supplier/requests` | кабинет поставщика (только поставщик) |
| GET | `/stock` | остатки |
| GET | `/products/{id}` | карточка продукта |
| GET | `/batches` | партии и сроки |
| POST | `/batches/{id}/adjust`, `/batches/{id}/write-off`, `/batches/write-off-expired` | корректировка и списание |
| GET, POST | `/supplies`, `/supplies/{id}/receive`, `/supplies/{id}/cancel` | поставки |
| GET | `/supplies/recommendations` | что заказать |
| GET, POST | `/orders` | заказы |
| GET, PUT, POST | `/dishes` | блюда и рецепты |
| GET | `/stop-list`, `/hot-offers`, `/stats`, `/alerts`, `/summary` | мониторинг |
| GET, PUT | `/settings` | настройки |
| GET | `/events` | поток обновлений (SSE) |

## Демо-данные

18 продуктов, 12 блюд, 6 поставок и около 170 заказов за неделю. Специально есть проблемные места:
просроченный лосось, мало огурцов, сливки с критическим сроком и одна непринятая поставка.
Если её принять, блюда возвращаются из стоп-листа. Ещё есть две заявки от «ООО Фермер», которые ждут решения,
одна вчерашняя, принятая частично (18 кг из 20), несколько списаний в корзине и закреплённые «Драники» (сезонное).
