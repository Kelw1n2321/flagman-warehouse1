# «Флагман» — мониторинг ресторанного склада

Система учёта движения продуктов, партий и сроков годности, проверки заказов, автоматического стоп-листа и «горячих предложений».
Интерфейс — рабочий светлый дашборд: категории и фильтры слева, карточки продуктов с подписанными показателями
в центре, панель оперативного контроля справа, разделы — вкладками под шапкой (на телефоне — нижней панелью).
Есть светлая и тёмная тема: по умолчанию как в системе, переключатель в шапке, выбор запоминается в браузере.
Цен, корзины покупателя и торговых механик нет.

## Запуск

Нужны .NET 10 SDK и Node.js 20+ (в этой папке Node лежит портативно в `.tools/node`).

```bash
cd frontend && npm install && npm run build
```

```bash
cd backend/Flagman.Api && dotnet run
```

Откройте <http://localhost:5080>. При первом запуске создаётся SQLite-база `backend/Flagman.Api/App_Data/flagman.db`
с демо-историей за неделю. Сбросить демо-данные можно в «Настройках».

Режим разработки интерфейса с горячей перезагрузкой: `cd frontend && npm run dev` → <http://localhost:5173> (запросы `/api` проксируются на :5080).

**Производственный режим (PostgreSQL):** `docker compose up --build` → <http://localhost:8080>. Провайдер БД выбирается
настройкой `Database:Provider` (`sqlite` | `postgres`), строка подключения — `ConnectionStrings:Postgres`.
В этом режиме демо-данные не создаются (`Demo:SeedOnStart=false`), сброс отключён (`Demo:AllowReset=false`).

### Деплой на Render

В корне лежит `render.yaml` (Blueprint, Docker, бесплатный план). Запушьте репозиторий на GitHub,
затем в Render: **New → Blueprint → выбрать репозиторий → Apply**. Порт берётся из `$PORT`, health-check — `/api/v1/summary`.
Демо-база SQLite живёт внутри контейнера: после перезапуска или «засыпания» бесплатного сервиса она пересоздаётся
со свежей демо-историей (даты считаются от текущего момента).

### Правила учёта

* Остаток продукта нигде не хранится — он всегда суммируется из партий. Партия принадлежит одной поставке и одному продукту,
  срок годности хранится у партии. Один продукт в одной поставке может прийти несколькими партиями с разными сроками.
* Просроченная партия (момент окончания срока включительно) не входит в доступный остаток и не используется для блюд;
  её количество показывается отдельно до списания (вручную или автоматически — переключатель в настройках).
* Каждая операция (приёмка, расход на заказ, списание просрочки/порчи, корректировка) пишется в журнал движения
  с остатком партии после операции.
* **Заказ:** потребность суммируется по всем блюдам → сравнивается с доступным остатком → если не хватает хоть одного
  ингредиента, заказ сохраняется как отклонённый с перечнем нехватки (сколько нужно / доступно / просрочено) и остатки
  не меняются. Иначе сначала строится полный план FEFO, затем все партии меняются в одной транзакции.
  Команды сериализуются (`WriteGate`), у партии есть токен версии — отрицательных остатков и частичных списаний не бывает.
* **Стоп-лист** вычисляется из того же среза, что и остатки (блюдо в стопе, если хоть одного ингредиента меньше нормы на порцию),
  поэтому пересчитывается после любой операции, изменения рецептуры и просто с течением времени: фоновый монитор каждые 30 с
  сверяет статусы партий, предупреждения и интервалы стоп-листа (для статистики частоты).
* **Сроки:** пороги настраиваются (по умолчанию > 72 ч — норма, 24–72 ч — скоро истекает, ≤ 24 ч — критический, после — просрочено).
  Время хранится в UTC; дата окончания, введённая при приёмке, трактуется в часовом поясе ресторана (`Europe/Moscow` по умолчанию),
  «сегодня/завтра» в интерфейсе считается по границе суток этого пояса.

### Горячие предложения

Для каждого ингредиента блюда, у которого есть пригодные партии в зоне «скоро истекает»/«критично»:

```
вклад = 100 × срочность × (0,35 + 0,65 × покрытие) × (0,5 + 0,5 × объём) × эксклюзивность
```

* срочность — 0,4 на пороге «скоро истекает», линейно растёт до 1,0 к моменту окончания срока ближайшей партии;
* покрытие — какую долю продукта под угрозой блюдо реализует с учётом доступных порций (их ограничивают остальные ингредиенты);
* объём — сколько порций этого блюда нужно, чтобы израсходовать продукт (насыщение на 20 порциях);
* эксклюзивность — 1/√N, где N — число доступных блюд с этим продуктом.

Приоритет блюда — сумма вкладов (≥ 45 — высокий, ≥ 20 — средний). Для каждого блюда выводится текстовое объяснение,
разложение по факторам, число доступных и рекомендуемых порций. Блюда, которые спасли бы продукт, но сами в стоп-листе,
показываются отдельно с причиной.

### Прогноз и рекомендации поставок

Средний расход за окно (7 дней) → почасовое моделирование на неделю вперёд: расход идёт по FEFO, партия, срок которой
наступил раньше, чем её израсходовали, выбывает (ожидаемые потери). Отсюда: момент исчерпания продукта, момент попадания
блюда в стоп-лист и рекомендуемый объём поставки на N дней (с учётом минимума и ожидаемых потерь).

## API (`/api/v1`)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/stock?search&category&filter&sort` | складские остатки по продуктам |
| GET | `/products/{id}` | продукт: партии, журнал, поставки, блюда, прогноз |
| GET | `/batches?expiry&productId&category&includeClosed&search` | партии и их сроки |
| POST | `/batches/{id}/adjust`, `/batches/{id}/write-off`, `/batches/write-off-expired` | корректировка и списания |
| GET/POST | `/supplies`, `/supplies/{id}`, `/supplies/{id}/receive`, `/supplies/{id}/cancel` | поставки и приёмка партий |
| GET | `/supplies/recommendations` | анализ и предложение поставок |
| GET/POST | `/orders`, `/orders/{id}` | заказы (отклонённый — 409 с причиной) |
| GET/PUT/POST | `/dishes`, `/dishes/{id}` | блюда и рецептуры |
| POST | `/dishes/availability-check` | проверка возможности приготовления без списания |
| GET | `/stop-list`, `/hot-offers`, `/stats?days&category`, `/alerts?status`, `/summary` | мониторинг |
| POST | `/alerts/acknowledge` | обработка предупреждений |
| GET/PUT | `/settings` | пороги, часовой пояс, автосписание, генератор событий |
| GET | `/events` | SSE-поток изменений склада |

Ошибки возвращаются в формате ProblemDetails с понятным текстом и ошибками по полям; изменяющие запросы ограничены по частоте.

## Демо-данные

18 продуктов, 12 блюд с рецептурами, 6 поставок (одна ожидает приёмки), около 170 заказов за неделю. История не нарисована вручную: поставки,
заказы и утренние списания проигрываются через те же команды, что использует интерфейс, поэтому остатки, журнал,
стоп-лист и статистика согласованы. В исходном состоянии: лосось просрочен (две рыбные позиции в стоп-листе), огурцов
60 г (салат в стоп-листе), сливки с критическим сроком, молоко с просроченной партией, куриное филе 18,5 кг в трёх
партиях с разными сроками, мало яиц; в «Поставках» ждёт неподтверждённая поставка рыбы и огурцов — её приёмка возвращает
блюда в меню. Генератор событий (настройки) эмулирует поток заказов и поставок через те же API.

## Ограничения

* Схема БД создаётся через `EnsureCreated`; для эксплуатации на PostgreSQL стоит перейти на EF-миграции.
* `WriteGate` сериализует команды внутри одного процесса; при нескольких экземплярах защиту даёт токен версии партии
  (конфликт → 409 «повторите»), но для высокой нагрузки нужны блокировки строк на стороне БД.
* Статистика считается в памяти по всему журналу — рассчитано на объём одного ресторана.
* Авторизации нет: это внутренний терминал склада.
